# 3. Critical anti-fabrication rule

Do NOT manufacture a performance improvement.

Do NOT write:

```text
Query became 70% faster
```

unless actual measurements demonstrate that result.

Do NOT claim:

* index improved performance
* sequential scan was replaced
* execution time decreased
* query planner selected an index
* query became more efficient

unless the actual PostgreSQL execution plan and timing support the claim.

If an optimization produces little or no improvement, that is a valid engineering result.

Document it.

# 6. Establish a clean baseline

Before modifying indexes or query structure, establish the baseline.

For each selected workload:

1. execute the query normally
2. execute `EXPLAIN (ANALYZE, BUFFERS, VERBOSE)`
3. capture the actual plan
4. record execution time
5. record planning time where available
6. record relevant buffer statistics
7. identify the major plan nodes

Pay attention to:

* Sequential Scan
* Index Scan
* Bitmap Heap Scan
* Hash Join
* Nested Loop
* Merge Join
* Sort
* HashAggregate
* GroupAggregate
* WindowAgg
* rows estimated vs actual
* loops
* shared hit blocks
* shared read blocks
* sort method
* memory usage

Do not simply paste an execution plan into the repository without interpreting it.

---

# 7. Understand PostgreSQL planner behavior

For each baseline workload, identify:

### Access path

Is PostgreSQL using:

* sequential scan?
* index scan?
* bitmap scan?

### Join strategy

Where joins exist, determine whether PostgreSQL uses:

* Hash Join
* Nested Loop
* Merge Join

and why that strategy is plausible.

### Aggregation

Identify:

* HashAggregate
* GroupAggregate
* other aggregation nodes

### Sorting/windowing

Identify expensive:

* Sort
* WindowAgg
* ranking operations

### Cardinality

Compare:

```text
estimated rows
vs
actual rows
```

Large discrepancies should be considered as possible planner-estimation issues.

Do not automatically assume that every sequential scan is bad.

A sequential scan over a large fraction of a table can legitimately be faster than using an index.

This distinction is important.

# 12. Query-level optimization

Where appropriate, investigate whether query structure itself contributes to cost.

Potential areas include:

# 14. Run multiple measurements

Single-run timing is noisy.

Where practical, run each benchmark multiple times.

Record enough repetitions to distinguish an obvious performance difference from normal execution variance.

At minimum capture:

* baseline execution time
* optimized execution time

Prefer reporting:

* multiple runs
* median
* minimum/maximum where useful

Do not create artificial precision.

For example, do not report:

```text
12.384729 ms
```

if PostgreSQL/environment variability makes that precision meaningless.

Use the actual values produced by the experiment.

---

# 15. Cache-awareness

Recognize that PostgreSQL caching can affect measurements.

Record whether the workload was executed against:

* warmed cache
* cold-ish cache
* mixed conditions

Do not claim a cold-cache benchmark unless the experiment actually established that condition.

For the primary comparison, consistency is more important than pretending to simulate production perfectly.

A practical approach is to compare repeated executions under the same database state and clearly document the methodology.

---

# 16. Buffer analysis

Use:

```text
EXPLAIN (ANALYZE, BUFFERS)
```

for the important experiments.

Interpret:

* shared hit
* shared read
* local blocks where applicable
* temporary blocks where applicable

Use this to support performance conclusions.

For example:

```text
execution time decreased
+
shared buffer reads decreased
```

is stronger evidence than execution time alone.

Do not force this outcome.

If buffers do not improve, report that.

# 17. Avoid misleading conclusions

Do NOT use the following simplistic rule:

```text
Index exists → query is faster
```

Instead understand:

```text
Index usefulness depends on:
selectivity
query predicates
table size
data distribution
join structure
ordering
planner cost estimates
cache state
```

A sequential scan may legitimately remain optimal.

If PostgreSQL chooses a sequential scan despite an index, explain why that can be reasonable.

This explanation itself is valuable interview material.
