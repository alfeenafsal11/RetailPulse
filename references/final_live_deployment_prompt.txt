# RetailPulse — LIVE DEPLOYMENT EXECUTION

## Phase

PHASE_08_LIVE_DEPLOYMENT

## Objective

Deploy the completed RetailPulse project to a real public environment and obtain a **working public Streamlit URL** suitable for inclusion in the project's application/resume.

This is a deployment-only phase.

The RetailPulse implementation is already complete and locally validated. Do not redesign the application or add new functionality.

The required final outcome is:

```text
Real hosted PostgreSQL
        ↓
Real Streamlit Community Cloud application
        ↓
Publicly accessible RetailPulse URL
        ↓
End-to-end validation
```

# 3. HOSTED POSTGRESQL

Provision a legitimate managed PostgreSQL instance.

Prefer a simple managed PostgreSQL provider appropriate for a small portfolio project.

Do not introduce unnecessary infrastructure such as:

* Kubernetes
* Docker-based production orchestration
* Spark
* Kafka
* Airflow
* dbt
* Redis
* custom backend services

A conventional managed PostgreSQL database is sufficient.

If a provider is already available through the authenticated environment, use it.

If no provider authentication is available, determine whether deployment can be completed through an existing authenticated browser/session.

If authentication is required and unavailable, **STOP at that boundary and report the exact manual authentication action required from the user.**

Do not fabricate credentials, database hosts, connection strings, provider resources, or deployment URLs.

# 5. PRODUCTION DATABASE VALIDATION

Run validation directly against the hosted PostgreSQL database.

Verify:

### Row counts

```text
customers    = 10,000
products     = 500
transactions = 245,210
```

### Revenue

```text
$53,581,128.12
```

### Integrity

Verify:

* primary-key uniqueness
* foreign-key integrity
* transaction/customer relationships
* transaction/product relationships
* quantity validity
* price validity
* discount validity
* amount calculation consistency

### Timestamp range

Verify:

```text
MIN(transaction_timestamp)
MAX(transaction_timestamp)
```

and reconcile it against the authoritative local dataset.

### Analytical reconciliation

Execute the existing analytical SQL against the hosted database.

Verify at minimum:

* total revenue
* transaction count
* active customers
* AOV
* repeat purchase rate
* RFM population
* category revenue
* revenue concentration
* cohort output
* top customer output

Production analytical results must match the validated local results.

If any discrepancy exists:

1. Diagnose it.
2. Determine whether it is a migration/data/configuration issue.
3. Fix the issue.
4. Rerun validation.

Do not silently accept unexplained discrepancies.

# 6. DATABASE CONNECTION SECURITY

Production credentials must NEVER be committed to Git.

Use Streamlit's supported secrets mechanism for the deployed application.

The repository may contain:

```text
.env.example
```

with placeholders only.

The repository must NOT contain:

* database password
* database connection URI containing credentials
* cloud API keys
* provider tokens
* OAuth tokens
* Streamlit secrets
* private keys

Production configuration must be separate from local development configuration.

Conceptually:

```text
Local:
.env
    ↓
local PostgreSQL

Production:
Streamlit Secrets
    ↓
hosted PostgreSQL
```

Do not commit either secret store.
