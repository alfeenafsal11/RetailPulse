# 2. Phase objective

Build the **core analytical SQL layer** for RetailPulse.

The objective is to answer realistic retail/customer-business questions using PostgreSQL rather than merely demonstrating isolated SQL syntax.

The analytics must support the project's central business question:

> Which customers, products, and customer segments are driving revenue and retention, and which customers should a retail engagement platform prioritize for intervention?

The resulting SQL should demonstrate practical competence in:

* SELECT/filtering
* aggregations
* GROUP BY
* JOINs
* date/time analysis
* CTEs
* window functions
* conditional aggregation
* customer-level metrics
* segmentation
* cohort analysis
* revenue concentration
* business-oriented interpretation

This phase must produce **reusable SQL artifacts**, not merely one-off commands executed interactively.

total revenue / total transactions

customers with >=1 transaction

# 8. RFM segmentation

Implement **actual RFM analysis in SQL**.

Do not use:

```text
customer_segment_ground_truth
```

to determine RFM segments.

That field is generation-time ground truth only.

RFM must be independently derived from observed transactions.

Calculate:

### Recency

Time since the customer's latest purchase.

### Frequency

Number of transactions/orders.

### Monetary

Total customer revenue.

Choose defensible scoring logic.

A practical implementation may use PostgreSQL window functions such as:

```text
NTILE(5)
```

to generate 1–5 scores.

Document:

* recency scoring direction
* frequency scoring direction
* monetary scoring direction
* how the final segment is assigned

For example, higher recency quality should correspond to more recent activity.

Do not hard-code arbitrary customer IDs into segments.

---

# 9. Customer segment definitions

Create business-readable RFM segments.

At minimum consider segments such as:

```text
Champions
Loyal

At Risk

```

The exact threshold logic should be justified and documented.

Important:

The synthetic generator already contains five behavioral archetypes. The SQL segmentation must remain independent.

After calculating SQL-derived RFM segments, compare them against `customer_segment_ground_truth` only as an **analytical validation/exploration**, not as the segmentation mechanism.

If you perform this comparison, clearly label it as a comparison between:

```text
latent generation archetype
        vs
observed RFM-derived segment
```

Do not claim that they should match perfectly.

# 13. Revenue concentration

Implement revenue concentration analysis.

At minimum calculate the share of total revenue contributed by:

```text
Top 1%
Top 5%
Top 10%
Top 20%
```

of customers, or use the implementation plan's specified concentration thresholds if different.

Use window functions where appropriate.

Do not simply sort customers and manually inspect the result.

The SQL should calculate cumulative revenue and cumulative revenue percentage.

This is important because it creates a realistic business insight:

> How dependent is revenue on a small fraction of customers?

# 16. SQL quality requirements

Write production-style SQL where practical.

Use:

* meaningful aliases
* consistent formatting
* explicit joins
* CTEs when they improve readability
* window functions where analytically appropriate
* comments for non-obvious business logic

Avoid:

* `SELECT *` in reusable analytical outputs unless genuinely appropriate
* deeply nested unreadable queries
* duplicated logic
* arbitrary magic numbers without comments
* unnecessary subqueries
* accidental Cartesian joins

Do not optimize queries prematurely in this phase.

Phase 4 is specifically dedicated to performance diagnosis and optimization.

---

# 17. Validate every analytical query

Every major analytical query must actually be executed against PostgreSQL.

Do not validate SQL by syntax inspection alone.

For each query verify:

* it executes successfully
* returned columns are correct
* row counts are reasonable
* values are internally consistent
* joins do not unexpectedly multiply rows
* calculations produce plausible results

Record actual outputs or summary results where useful.

Do not fabricate analytical findings.

---

# 18. Cross-check important metrics

Where possible, independently verify important calculations.

For example:

```text
total revenue from KPI query
        =
total revenue from direct transactions aggregation
```

Likewise verify:

```text
customer-level revenue sum
        =
overall revenue
```

and:

```text
category revenue sum
        ≈
overall revenue
```

according to the chosen treatment of all transaction records.

Investigate any discrepancy.

This is especially important for detecting accidental row multiplication during joins.

---

# 19. Validate joins explicitly

Because JOIN performance and correctness are central to the project, perform sanity checks for the major joins.

For example:

```text
transactions
JOIN customers
```

should not increase the number of transaction rows.

Likewise:

```text
transactions
JOIN products
```

should not increase the number of transaction rows.

Validate this explicitly.

If a join unexpectedly multiplies rows, investigate and correct the SQL.

# 20. Analytical tests

Create an appropriate test/validation mechanism under `tests/` for the SQL analytics.

The tests should validate important invariants rather than merely checking that files exist.

Examples:

### Revenue conservation

Sum of category revenue should reconcile with total revenue.

### Customer revenue conservation

Sum of customer-level revenue should reconcile with total revenue.

### RFM assignment

Each eligible customer should receive exactly one RFM segment.

### Cohort consistency

Retained customers cannot exceed the cohort population for the relevant cohort/month.

### Revenue concentration

Cumulative revenue percentage should be monotonic.

### Transaction join integrity

Joining transactions with dimensions should preserve transaction row count.

Use actual PostgreSQL execution.
