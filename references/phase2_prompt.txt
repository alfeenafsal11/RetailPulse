# 2. Phase objective

Implement the **PostgreSQL database layer** for RetailPulse and load the deterministic Phase 1 synthetic retail dataset into it.

The target is a clean, analytically useful relational/star-schema foundation that will support:

* customer analytics
* product/category analytics
* transaction/revenue analytics
* RFM segmentation
* cohort retention
* revenue concentration
* SQL query-performance experiments in Phase 4

This phase is about **database/schema/loading correctness**.

Do NOT implement the analytics layer, dashboard, performance experiment, or deployment yet.

# 5. Database design

Create a PostgreSQL schema appropriate for analytical workloads.

At minimum establish:

```text
customers
products
transactions
```

Use appropriate:

* primary keys
* foreign keys
* data types
* NOT NULL constraints where justified
* CHECK constraints where appropriate
* indexes where justified

Do not blindly index every column.

The project specifically needs to demonstrate understanding of query performance, so indexes should be deliberate and explainable.

Consider the analytical access patterns that later phases will need, particularly:

* transactions by customer
* transactions by product
* transactions by timestamp/date
* joins between transactions and dimensions

Document the rationale for important indexes.

---

# 6. Data types and integrity

Use PostgreSQL-native types appropriately.

Examples:

* IDs → integer/bigint as appropriate
* dates → `DATE`
* timestamps → `TIMESTAMP` or `TIMESTAMPTZ`, based on the actual project convention
* prices/revenue/cost → `NUMERIC` rather than floating-point where monetary exactness matters
* quantity → integer/numeric as appropriate
* categorical fields → appropriate textual types

Ensure:

```text
amount = quantity * unit_price - discount
```

is preserved by the loaded data.

Do not silently round or materially transform monetary values during loading.

If the CSV representation requires a transformation for PostgreSQL storage, document it.

# 8. Loading strategy

Load:

1. customers
2. products
3. transactions

in a dependency-safe order.

The final database must contain approximately:

* 10,000 customers
* 500 products
* 245,210 transactions

Do not invent or fabricate counts.

After loading, query PostgreSQL and record the actual counts.

Verify that:

* every transaction references an existing customer
* every transaction references an existing product
* transaction IDs are unique
* customer IDs are unique
* product IDs are unique
* monetary fields are valid
* quantities are valid
* timestamps are valid

Also verify the transaction date range against Phase 1:

```text

```

Use actual database queries for these checks.

# 9. Database validation

Create appropriate validation tests/scripts for Phase 2.

At minimum validate:

### Row counts

```text
customers = 10,000
products = 500
transactions = 245,210
```

using actual loaded values.

### Primary-key uniqueness

Verify all relevant primary keys.

### Foreign-key integrity

Verify transaction → customer and transaction → product relationships.

### Null/integrity checks

Check important required columns.

### Monetary consistency

Check that the stored transaction amount corresponds to:

```text
quantity * unit_price - discount
```

within the exact precision convention selected for the database.

### Date range

Verify the earliest and latest transaction timestamps.

### Basic analytical sanity

Compare database aggregates against the source CSV where useful, such as:

* total transaction count
* total revenue
* minimum/maximum transaction amount
* revenue by category

The purpose is to establish that loading did not alter the dataset.

# 11. Indexing

Implement only indexes justified by the project's expected analytical queries.

At minimum think about the access patterns around:

```text
transactions.customer_id
transactions.product_id
transactions.transaction_timestamp
```

and relevant join keys.

Do not prematurely create an excessive number of indexes.

For every nontrivial index, document:

1. what query/access pattern it supports
2. why it is useful
3. whether it has a meaningful storage/write tradeoff

This will become important in Phase 4.

Do not claim that an index improves performance unless it has actually been benchmarked.
