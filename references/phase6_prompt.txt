# 2. Phase objective

Build a **clean, functional Streamlit dashboard** that communicates the project's analytical findings using the existing Python analytics layer.

The dashboard should answer:

> What is happening in the retail business, which customers matter most, where is revenue coming from, and where should customer engagement efforts be focused?

The application should demonstrate:

* live database-backed analytics
* SQL/Python integration
* business-oriented data visualization
* customer segmentation
* retention analysis
* revenue analysis
* clear analytical communication

This is intended to become the project's **live hosted data analytics project**.

---

# 3. Critical architecture rule

Do NOT bypass the existing architecture.

The dashboard must use:

```text
Streamlit
    ↓
src/analytics/analytics.py
    ↓
sql/analytics/*.sql
    ↓
PostgreSQL
```

Do not make the dashboard directly execute ad-hoc SQL everywhere.

Do not load the raw transaction CSV into Streamlit and perform the entire analytics workload in pandas.

Do not duplicate the SQL analytical logic in the dashboard.

The existing Python analytics layer is the dashboard's interface.

# 18. Business interpretation

The dashboard should not merely display charts.

Where useful, add concise text explaining what a visualization answers.

Examples:

```text
Customer Segmentation
RFM segmentation identifies customers based on observed purchasing behavior.

Cohort Retention
Retention is measured relative to each customer's first observed purchase month.

Revenue Concentration
This shows how cumulative customer revenue changes as progressively larger portions of the customer base are included.
```

Keep interpretations factual.

Do not invent causal explanations.

Do not claim that a customer segment "will churn" unless the analysis actually establishes that.

# 20. Data refresh behavior

The dashboard should retrieve analytical data from PostgreSQL.

Use Streamlit caching appropriately if useful, such as caching database-derived data for a reasonable duration.

However:

* do not cache indefinitely
* do not cache secrets
* do not create stale-data behavior that is difficult to understand

If the dataset is static for this project, a modest cache is acceptable.

Document the chosen approach.

---

# 21. Database failure handling

If PostgreSQL is unavailable, the application should fail clearly.

Do not silently switch to:

* CSV
* SQLite
* hard-coded sample values

A useful user-facing message can explain that the PostgreSQL backend is unavailable.

Do not expose passwords or connection details.
